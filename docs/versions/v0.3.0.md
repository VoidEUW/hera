# v0.3.0 — the widening pass

**Status:** planned, not started · **Written:** 2026-08-31 · **Follows:** v0.2.0

v0.2 is *organise → produce → make room → remember*. This is what comes after it, and it exists as a
document now for one reason: **dreaming moved here out of v0.2**, and a feature that moves needs
somewhere to land or it becomes a feature that was forgotten.

## What moved, and why

**Dreaming and experience training** — v0.2.0's M5, and
[ADR 17](../adr/) with it. Not because it stopped being wanted, and not because it turned out to be
harder than it looked. Because **the four milestones under it want to be stable first**, and a
version that ships five things half-settled is worse than one that ships four things you can rely
on. That is the call the person building this made, and it is the right shape of call to make: this
is the release where Hera becomes something to use daily, and daily use is what finds the things a
plan cannot.

It is also the *only* v0.2 milestone that costs nothing to defer, which is worth writing down
because it is not obvious from the milestone list. Every dependency arrow points **into** dreaming
and none point out of it: it reads memories and proposes to the mind, so both have to exist first,
and nothing else in v0.2 waits on it. Projects, artifacts, the redesign and memory are each usable
the day they land. Dreaming deferred leaves no half-built seam behind — `hera_profiles.propose()`
and the `evolvable` tier already exist and already guard the thing dreaming would touch.

What that costs, said plainly rather than hidden: Settings → Dreaming stays a disabled tab for
another version, and the promise in `README.md` — that she re-reads her own conversations and offers
changes to herself — stays a promise. `frontend.md` § *Settings* already holds the line that makes
this bearable: **a feature you can see coming is a promise, one you cannot is a surprise.**

## `hera-code` — a second application on the same packages

A note rather than a plan, and the shape of it is already clearer than most notes.

**What it is.** A command-line coding agent, in the register Claude Code and Codex CLI occupy: a
terminal, a model, tools that read and write a working tree, and skills. Built on **this
workspace's packages** rather than beside them — `hera_providers`, `hera_prompts`, `hera_skillsets`,
`hera_tools`, `hera_permissions`, `hera_storage`. It carries its own built-in MCP server the way
Hera carries `hera_mcp`, holding the tools a coding agent needs and Hera has no business having.

**Why it is worth doing beyond wanting the tool.** Two packages in this repository carry a claim
that has never been tested: `hera_storage` and `hera_prompts` "contain no domain concept at all and
must stay liftable into an unrelated project" (CLAUDE.md). A second application is the only thing
that can *check* that claim rather than assert it — and every leak it finds is a leak that is
already in Hera, being paid for quietly. Shared implementation also means a bug is found once and
fixed once, which is the reason the person building this wants it.

**How Hera reaches it, and the part that is nearly free.** Hera already reads `~/.hera/mcp.json` in
the Claude-Desktop `mcpServers` shape, and `hera_tools` already mounts whatever it finds there
without knowing what it is. So *she can drive a coding CLI running somewhere else* may need *no new
mechanism in Hera at all* — hera-code is an entry in that file. Worth verifying rather than
assuming, but if it holds, the feature is a document and a binary rather than a milestone.

That makes hera-code a **third position** in the MCP arrangement this repository already has, and
naming it keeps the two existing ones from blurring:

| | |
|---|---|
| `hera_mcp` | the server she **is** — in-process, mounted by the application |
| `hera_tools` | the client she **has** — mounts any server, knows nothing about hers |
| `hera-code` | a server she **reaches** — a separate process over a real transport |

**The question it opens, which is a permissions question and not a transport one.** A tool that
edits a working tree on another machine is exactly the case `DEFAULT_POLICY` exists to ask about
rather than allow. `hera__*` is allowed without a card because it is hers and bounded; nothing about
that reasoning extends to a CLI with a shell. This wants deciding before it is wired, not after.

**Two things genuinely undecided.** Whether hera-code lives in this repository as a second `apps/`
member — nearly free, the uv workspace already does it, and it keeps the packages honest by
building both in one CI run — or in its own repository consuming published packages, which is a
real packaging decision this project has never had to make. And whether it talks to a *remote* Hera
at all, or only to a local one; "from far away" is a different security posture from "on this
machine", and the second is where it should start.
