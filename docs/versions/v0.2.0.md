# v0.2.0 — the deepening pass

**Status:** planned · **Written:** 2026-08-28 · **Follows:** v0.1.0, the spine

v0.1.0 made the spine run. A message typed into the browser reaches the model through the skill
router, the mind and the turn orchestrator, and comes back as Server-Sent Events the interface
renders — with tools, permissions and her own stance along the way.

What it does not do is **accumulate**. Every conversation starts from nothing. She cannot produce a
thing you keep, only prose you copy out of a code fence. Projects are a database row with no way to
make one. And the two packages `ARCHITECTURE.md` names as v0.2 — `hera_memories` and
`hera_promptevo` — do not exist as directories.

This version is the pass that fixes that, in the order the work unblocks itself:

**organise → produce → make room → remember → reflect**

That order is not aesthetic. Artifacts and memory both want a panel beside the conversation, so the
redesign sits between them rather than after both. Dreaming reads memories and proposes to the mind,
so it cannot be third. Projects are first because they are almost built already and everything else
gets filed under them.

## What reading the repository changed

Three findings moved this plan away from what it looked like on paper.

**Projects are already built on the server.** `hera_chats.Project` carries `instructions`,
`pinned_skills` and `default_profile_id`; `hera_core.api.projects` is complete CRUD;
`hera_chats.turn` already binds `SLOT_PROJECT` and already merges project pins behind chat pins;
`Rail.svelte` already discloses a project's chats inline. The gap is entirely interface — **there is
no way to create or edit a project.** So M1 is a screen and two columns, not a feature.

**There is no dream ADR.** The design worth keeping is in [`prototype.md`](../prototype.md) — the
memory tiers and their separate caps, the dedup thresholds, the governance split between `write()`
and `propose()`, the dream log — and it is retired German prose, not a decision record. Part of this
version is writing those records, because the prototype is explicitly *wrong about everything
structural* and citing it as authority is how the old shape comes back.

**`hera_skillsets.render` tells the model a lie.** Every selected skill with files beside it arrives
with the sentence *"This skill has further files beside it in `<path>`. Read one if this skill tells
you to."* She has no tool that can read a file. This is the actual reason Anthropic's
reference-heavy skills do not work, and it is one small tool away from being true.

## The line on Anthropic's skills

Anthropic's published skills want two things Hera lacks: reading a skill's bundled reference files,
and running its bundled Python scripts. **v0.2 does the first and not the second.**

That splits them cleanly rather than half-supporting all of them. `brand-guidelines`,
`canvas-design`, `dataviz`, `frontend-design` and `web-artifacts-builder` are reference-heavy — they
read `references/*.md` and emit a document, which is exactly artifacts plus resource reading.
`pptx`, `docx` and `xlsx` shell out to Python, and will say so plainly instead of failing strangely.

**The sandbox was pulled into this version and then put back.** The reasoning is worth keeping,
because the mistake is one that is easy to make twice: it looked like a prerequisite for artifacts,
and it is not. `markdown`, `code`, `mermaid`, `html` and `svg` are *content* — an HTML artifact is a
sandboxed `iframe` in the browser, not a container on the host. The only thing running code is
load-bearing for is the script-running half of the skills above, which is a smaller prize than a
Docker dependency and a security claim to keep true.

What the excursion did produce is worth having:
[ADR 15](../adr/0015-running-code-in-a-container.md) answers the question
[`tooling.md`](../tooling.md) § 3 refused to let the sandbox start without — *a small sandbox for
testing, or safe?* — and that answer does not expire. It is the record v0.3 picks up from.

## The milestones

### M1 — Project folders — ✅ done

A project is a container with **behaviour**, not a folder — a name, its own instructions, its own
pinned skills, a default profile, and later its own files. [`frontend.md`](../frontend.md)
§ *Project or profile?* holds the line this depends on: a profile answers *who she is*, a project
answers *what we are working on*, and if a sentence would still be true in a project about something
else, it belongs in a mind region instead.

**Two columns.** `Project.default_agent_id` is the seam for agent selection — a bare `UUID`, unused
by the turn, rendered as a disabled control saying v0.3. That is the same precedent as Settings →
Dreaming: a feature you can see coming is a promise, one you cannot is a surprise.
`Project.color` gives the rail row an accent, so a project reads as a place rather than as a nested
list. Migration `0004`.

**`ChatPatch` grows `project_id`.** *Move this chat into that project* is the one organising verb
missing, and it is a field on an endpoint that already exists rather than a new one.

**A project screen**, at `/project/<id>` — not a Settings tab. Settings is *how she works*; a
project is the work. It carries the instructions editor, the pinned-skill picker (`SkillPicker`
already exists and already writes a list of names), the default profile, the disabled agent
selector, and the chats inside.

**The rail gains the affordances it is missing:** a **＋** on the `PROJECTS` heading and a `⋯` menu
per project. That is the chat row's mechanics with different items, and the existing
`menuFor`/`renaming`/`confirming` triple is reused rather than reinvented — three separate ids
because only one can be true at a time, and one mode field would let *renaming* survive the menu
closing.

**Project files are not in M1.** `frontend.md` is right that they need embeddings; they land in M4.
Until then the screen shows no files section rather than an empty one.

**What building it turned up**, both found by driving the real interface rather than by a test:

- **Enter commits twice.** Pressing Enter in the new-project field ran the handler, which unmounted
  the input, which fired `blur` on the way out — so the name was submitted a second time. Renaming
  had survived that by accident since v0.1, because the second call compares against the name it
  just set and does nothing. Creating did not: it made *two* projects, and the pair raced closely
  enough for the same slug that the loser came back a 500. Both commits are now guarded by the state
  field that was already there.
- **A disclosed project's `⋯` drifted into its chat list.** `.more` is absolutely positioned against
  the nearest positioned ancestor, and a project's `li` is as tall as the whole group inside it — so
  the button centred itself somewhere over a chat row, where it was both unreachable and blocking
  the row underneath. The project's own line now has its own positioning context.
- **Every selector became one component**, which was not planned for M1 and belonged here anyway.
  The project screen's controls were bare native `<select>`s next to a composer whose two pills were
  a native `<select>` with `appearance: none` — matching in the one place somebody had bothered, and
  even there dropping the platform's own list into an interface that draws everything else itself.
  `Select.svelte` is the composer's pill plus the skill picker's popup, used by both, and the rail's
  `⋯` menus were given the same frame. This is a down payment on M3 rather than scope creep: the
  drawer that milestone builds needs the popup vocabulary settled first.
- **Left standing, and pre-existing:** two projects created *concurrently* with the same name still
  race in `ProjectRepository._free_slug`, which checks and then inserts, and the loser is a 500
  rather than `hera-2`. Sequentially it is correct and has a test. Nothing in the interface triggers
  it any more, so this is a note rather than a fix — the honest repair is catching `IntegrityError`
  and retrying, and it belongs with whatever next needs `create` to be safe under concurrency.

### M2 — Produce: a scratchpad, artifacts, and somewhere to run code

The largest milestone, and the one [`tooling.md`](../tooling.md) § 5 calls *"the least specified"*.
It is two branches, and the split is a dependency rather than a preference: `tooling.md` § 5 says
*"nothing here should start before the scratchpad question is answered, because they want the same
storage and answering them separately produces two."* So **scratchpad → artifacts**, and the first
is useful standing alone.

A third stage, the sandbox, was planned here and has gone back to v0.3 — see *The line on
Anthropic's skills* above for why, and for what the excursion left behind.

#### M2a — The scratchpad, and a tool call that knows its chat

[ADR 12](../adr/0012-a-chat-has-a-scratchpad.md). `~/.hera/chats/<chat id>/scratch/`, three tools
behind one optional `Scratchpad` port, and `hera__note` keeps its own description and stops being
used for something it never described.

**The part that unblocks everything else is smaller than it sounds and easy to get wrong.** No
tool can currently know which chat it is in: her server is built once at startup, and
`ManagedServer` runs every call as a child of a worker task created at *connect* time — so a
`contextvars.ContextVar` set around the turn reads back empty, silently. The answer is MCP's
`_meta`: `ToolRegistry.dispatch` takes an opaque `context` mapping, `hera_mcp`'s tools take a
`ctx: Context` the SDK keeps out of the input schema, and the key travels through
`ChatsSettings.chat_meta_key` exactly as `hera__ask`'s name travels through `asking_tools`.

This is also what `hera__remember(scope="chat")` has been missing since v0.1, which is the sign
the seam is in the right place.

#### M2b — Artifacts, and skill resources

[ADR 13](../adr/0013-artifacts-are-tool-calls-with-versions.md) and
[ADR 14](../adr/0014-skill-resources-are-readable.md).

**An artifact is a tool call.** ADR 11 draws the line at typesetting: the browser sets her prose and
reads no meaning back out of it. An artifact the interface *discovered* by hunting for a fenced block
with a filename in it would be a parser in the browser, which is the one rule this project does not
bend. So it produces an event like everything else, and — this is the part that makes it worth
building — it has an **identity and versions**. An artifact that can only be created is a file with
extra steps; the value is in changing the third step without re-emitting the whole thing.

**A new package, `hera_artifacts`**, importing `hera_storage` and `hera_home` and nothing else.
Tables `art_artifacts` and `art_versions`. **The content lives on disk**, at
`~/.hera/artifacts/<id>/v<N>.<ext>`, with the row as the index — because `CLAUDE.md` already promises
that nothing in `~/.hera` is a format you cannot open in an editor, and a diagram sealed inside a
SQLite blob breaks that promise on the first thing she makes that you want to keep.

An artifact belongs to a chat, and is listed at the project level when that chat is in one. That is
the second half of *a project has its own context*, and it is why M1 comes first.

**`hera_mcp` gains two ports and four tools.** `ArtifactStore` behind `hera__artifact_create`,
`hera__artifact_update` and `hera__artifact_read`; `ResourceReader` behind `hera__read_resource`,
which refuses `..` and absolute paths so a skill can only reach inside its own directory. Both ports
stay optional and answer *"not available in this deployment"* when unwired — the degradation story
ADR 4 asks for, applied to her own capabilities.

**`from_scratch` stays, and its reason moved.** Create and update accept a filename in this chat's
scratchpad instead of inline content. It was justified by the sandbox — a `.pptx` cannot come back
through a text tool result — and it earns its place without one: a long document she has been
drafting across several turns is already in the scratchpad, and re-emitting it into a tool argument
to make it an artifact would spend the whole thing through the context window twice.

**A diff-style edit is deliberately deferred.** `tooling.md` is right that re-emitting a whole
document is the cost, but a fourth tool whose description overlaps `update` is how a model ends up
choosing at random — and tool descriptions here are prompt text. Versions plus a rendered diff
deliver the visible half of the value; the edit tool is a v0.3 note with a reason attached.

**No new `ChatEvent` variant.** An artifact is a tool call and its result, exactly as an emotion is.
`ToolResultEvent.structured` already exists and is already `Any`; the create call returns
`{id, kind, title, version}` into it, and the card is drawn from that while the content is fetched by
id — so a 40 KB diagram never bloats the stored message. Routing a tool name to a card is what
`EmotionCard` already does, and it is not a parser: `structured` is typed JSON the server produced.

**Six kinds render**, and the interesting ones are the last two:

| kind | drawn with |
|---|---|
| `markdown` | `$lib/markdown.ts` and `Prose` — already exists, so nearly free |
| `code` · `text` | the fenced-code `figure` with its caption bar and copy button |
| `mermaid` | `mermaid`, lazily imported so it stays out of the initial bundle |
| `html` · `svg` | a sandboxed `iframe`, `allow-scripts` and deliberately **not** `allow-same-origin`, so the frame gets an opaque origin and cannot reach the app's storage |
| `file` | a name, a size and a download. What a `.pptx` is, and saying so beats rendering a wall of zip bytes |

**They stay allowed by default.** All of them are `hera__*`, which `DEFAULT_POLICY` allows, and that
is right — they write inside `~/.hera` and read inside the skills directory. The traversal guards are
what make it right, so they get tests of their own rather than comments.

### M3 — The redesign pass

[`frontend.md`](../frontend.md) says the design language gets adjusted once there is something to
argue with. There is now. The argument is written into that document **first** and built second —
it is the one place this project decides interface questions, and a change made in a component and
back-filled into the doc is a change nobody can disagree with before it exists.

**One drawer, not three.** Artifacts, memory and the dream log all want a panel beside the
conversation. It gets built once, here, before there are three of them. A drawer rather than a
modal, for the same reason Settings is a modal and the profile menu is not: this is something you
keep working with open.

**The rail carries more now** — projects with menus and colour, a search entry, and eventually
dreams. It wants the real hierarchy and the collapse-to-icons behaviour `frontend.md` § Chat already
draws and the build does not have.

**`⌘K` opens a command palette**, not Settings. It is listed as a known gap in both the changelog and
the status document, and the rail mock has said `🔍 Search ⌘K` since before there was a rail.

**The transcript and the activity gutter** are the two densest components in the interface and the
place every new event variant lands. What wants settling: the rhythm between an answer, a card and a
gutter block, and where an artifact card sits relative to the prose that produced it.

Two traps carry over from v0.1 and apply to everything touched here, both recorded in
[`status.md`](../status.md): `effect_update_depth_exceeded` stops Svelte rendering the page at all
with nothing on screen to say why, and both of its causes are shapes that look reasonable — assigning
`scrollTop` inside an `$effect` that also reads the state its own scroll handler writes, and calling
an initialiser from an `$effect` when that initialiser both reads and writes the same state.

### M4 — Memories

The half of `ARCHITECTURE.md`'s table that has been a promise since the rebuild started, and the
thing that unblocks project files and better skill retrieval at the same time.

**A new package, `hera_memories`**, declaring its own `Embedder` port rather than importing
`hera_providers`. One table, `mem_memories`, carrying the fields the prototype earned:
`kind · scope · text · chat_id · project_id · source · hits · negative_signals · enabled · embedding`.

**Retrieval, and why the caps are separate.** Cosine above a floor ranks first, then keyword overlap,
tiebroken on `hits` and then id; nothing matching at all falls back to newest-first. Each tier is
filtered and capped through its **own** budget rather than one shared pool — the prototype collapsed
them once and a noisy tier immediately crowded out a deliberately small one. Injected lines carry an
age hint, so she can tell *this was true in July* from *this is true*.

**Write-dedup on every path**, because the model will offer the same fact twice and should not be
punished for it: normalised equality plus cosine similarity against the same kind and scope bucket.
Pairs that are close but not close enough are not merged silently — they surface as review cards in
M5, which is a different decision from a threshold and belongs to a person.

**Keyword overlap is the default, not the degradation.** ADR 5 already settled that for skills and
the same reasoning applies harder here: a memory that silently stops arriving because embeddings are
down looks exactly like a memory that was never stored. An embedder that raises is treated as one
that is absent, and **a turn never fails on embeddings.**

**The landmine is known and has a name.** `SkillRouter.select()` is synchronous and `hera_chats` runs
it in a worker thread, so reaching the event loop from there means threading a loop handle down —
and getting it subtly wrong deadlocks a turn. That is why v0.1 left the embedder unwired rather than
half-wired. The answer is to compute the query embedding in the **async** part of the turn, before
the worker-thread hop, and pass it down — which is the same move that finally closes the seam for
skill retrieval.

Then `hera__remember` stops answering *"not available in this deployment"*, `SLOT_MEMORIES` gets
bound, project files land on top, and the drawer gets a memory panel with the `auto`/`manual` badge
that says which of them she wrote and which you did.

### M5 — Dreams

Last, because it reads memories and proposes to the mind, and both have to exist first.

**A new package, `hera_promptevo`** — the only place in this repository where the words *generation*,
*fitness* and *dream* are allowed. A run reads recent conversations and memories, prompts the model
in her own voice, and comes back with three kinds of candidate: a **mind-region rewrite**, a
**memory merge**, a **memory retirement**.

**Governance is the whole feature.** `hera_profiles` already ships the mechanism and it is the reason
this is safe to build: `write()` is the person's door and opens every region including `safety`;
`propose()` is everything else's and raises `RegionLocked` on an owner-fixed one. `hera_promptevo`
may only ever call the second. And the accept route checks the tier itself rather than trusting its
caller — the prototype learned that one the hard way, where a raw `POST /dream/accept kind=safety`
would otherwise have walked straight past the lock.

**Nothing is applied or deleted automatically.** Every candidate is a card: accept, reject, revert.
A rejection is information, not a deletion — it comes back as a counter-example in the next run,
which is what `README.md` has been promising since before any of this existed.

**Weak-memory signals inform the review and do not act on it.** Often-discarded and never-used are
both computed deterministically and both shown as *signal, not proof*. Nothing is pruned for you.

**The dream log is the transparency half**, and it is not optional: per run, the exact input
material, the system prompt, the thinking, the raw output and the candidate count, pruned to the last
thirty. Without it, a dream is a black box that rewrote her prompt.

The trigger is manual, from Settings → Dreaming, which stops being disabled. Scheduled dreaming stays
v0.3.

## Not in v0.2.0

Listed so a missing feature and a forgotten one do not look alike — the same courtesy v0.1.0's
*Known gaps* extended:

- **`hera__fetch`.** She can find a page and cannot read it, which is a worse place to stop than
  either end. It wants the same *turn this document into text* seam as PDFs, and a permission rule
  about the **argument** rather than the tool — `http://192.168.1.1/` is a request to a machine
  somebody chose. [`tooling.md`](../tooling.md) § 1.
- **PDFs.** Scoped into v0.1.0 and not built. Still roughly a day's work in the browser.
- **`hera_sandbox` and `hera_code_mcp`.** What the script-running Anthropic skills would need.
  Pulled into this version and put back — [ADR 15](../adr/0015-running-code-in-a-container.md) says
  what it would be and what it would claim, so this is a decision rather than an absence.
- **A diff-style artifact edit**, deferred with its reasoning in M2b.
- **The mobile sheet**, and **scheduled dreaming**, both v0.3.
- The open CodeQL finding on `ci.yml` — one `permissions: contents: read` block. Unrelated, cheap,
  worth doing in passing.

## Verification

Per milestone, not at the end. The fast loop is `-m "not e2e and not live"`; `live` needs a real
model endpoint and never runs in CI.

Three repository guards catch a structural mistake before anything else is worth running, and each
new package has to satisfy all three:

| Guard | What it demands of `hera_artifacts`, `hera_memories`, `hera_promptevo` |
|---|---|
| `tests/test_layering.py` | An explicit allow-list per package. `hera_mcp`'s stays **empty** — the new ports are ports precisely so it never imports any of these |
| `tests/test_workspace.py` | Member in `[tool.uv.workspace]`, entry in the root `[tool.uv.sources]`, in mypy's `files` and coverage's `source`, and no test module shadowing another |
| `tests/test_docs.py` | ADRs 12–15 indexed, numbered and given a status |

End to end, the check that actually proves each milestone:

- **M1** — create a project in the rail, write its instructions, move an existing chat into it, send a
  message, and confirm the instructions reached the prompt rather than merely being stored.
- **M2a** — over two turns of one chat, have her write a plan to the scratchpad and read it back in
  the next turn; confirm the file landed under that chat's id and not another's, that a second chat
  cannot see it, and that deleting the chat removes the directory.
- **M2b** — ask for a workflow diagram against a real endpoint: the call renders a card, the drawer
  draws the Mermaid, an update makes v2, and a reload shows exactly what was streamed. Separately,
  drop a reference-heavy Anthropic skill into `~/.hera/skills/` and confirm `hera__read_resource`
  reaches its `references/` and refuses `../`.
- **M3** — the existing Playwright specs still pass, plus new ones for the palette and the drawer.
  Watch for the blank page with no error, which is the reactive loop.
- **M4** — tell her something in one chat, start another, and see it recalled. Then kill the embedder
  and confirm the turn degrades to keyword overlap instead of failing.
- **M5** — dream over a handful of real conversations; confirm a `safety` proposal is refused at the
  route, that an accepted rewrite lands as a git commit carrying its `Hera-Origin` trailer, and that
  reverting restores the previous generation.

One branch per milestone. `main` is protected — pull request for everything, squash merge, linear
history — and [`status.md`](../status.md) § *Merging into `main`* records the two traps that have
already cost a blocked merge.
